# 冷链记录仪校时平台

单台冷链温度记录仪的校时网页：记录仪断电重启后时钟失准，数据员上传原始 CSV
（开机段号、本地秒数、温度），再为每个开机段录入两枚「本地秒数 ↔ UTC」校时锚点，
系统对两锚点之间的读数做线性校时，质检组即可按 UTC 日期读取可信的温度原始点。

主记录仪断流时，可再上传一台**备机记录仪**的 CSV（UTC、温度）和断流闭区间，
系统按「主机优先、备机补洞」规则生成可直接交付仓库的逐日合并温度。

技术栈：FastAPI + SQLite（WAL），服务端渲染页面 + JSON API，后台线程异步重算与合并。

## 快速启动（Docker Compose）

```bash
docker compose up --build
# 打开 http://localhost:8000
```

数据持久化在命名卷 `coldchain-data`（容器内 `/data/app.db`）。

本地开发（无需 Docker）：

```bash
pip install -r requirements-dev.txt
uvicorn app.main:app --reload        # http://localhost:8000
pytest -q                            # 运行自测
```

## 使用流程

1. **上传数据**（`/upload`）：CSV 三列 `segment,local_seconds,temperature`
   （支持中文表头 `开机段号,本地秒数,温度`，也支持无表头按此顺序）。
   - 累计最多 **2000** 点，超限整批拒绝；
   - 同一开机段内本地秒数不能重复（文件内或与已有数据），冲突整批拒绝；
   - 每批分配批次号，行号为 CSV 数据行序号（从 1 起）。
2. **校时锚点**（`/anchors`）：每段录入两枚锚点（本地秒数 1 < 本地秒数 2，
   且 UTC 必须递增）。两锚点之间的读数按线性插值校时；范围外或无锚点的读数
   **留存待校时**。**更正锚点必须提交所见版本**（乐观并发，版本不符返回 409）。
3. **按日查询**（`/query`）：按 UTC 日期查看已校时读数，每行显示
   **批次号、原行号、锚点版本**、校时版本；页面下方列出待校时读数及原因。
4. **处理状态**（`/`）：点数、重算状态（空闲/重算中/失败）、校时版本、
   数据代次、锚点与批次列表、备机文件与合并状态，可手动触发重算。

## 备机补数（断流补齐）

1. **备机补数**（`/backup`）：输入断流**闭区间**起止（UTC，起止均含），上传备机 CSV：
   `utc_time,temperature`（支持中文表头 `UTC时间,温度`，无表头按此顺序，最多 2000 点）。
   - **整批替换生效**：新文件入库即整体切换为当前备机文件，旧文件保留为历史；
     校验失败（编码、列数、时间格式、温度、超 2000 点、区间倒置）时整批拒绝，
     **仍沿用原备机文件**，不会出现半个文件。
   - 同一 UTC 存在**不同温度**时，记为该断流区间的冲突；合并结果标记
     **不可交付**，冲突 UTC 及涉事行号、温度原样列出。
     同一 UTC 同温的重复行不算冲突（合并时保留最小行号）。
2. **合并规则**：主机已发布读数**优先**；备机点仅在断流闭区间内、且与**任一**
   主机已发布读数相距**严格超过 5 秒**时补入（恰好 5 秒不补）。
   主机点不会因备机点被覆盖或删除。
3. **合并读数**（`/merged?date=YYYY-MM-DD`）：按 UTC 日展示合并结果，每行标注
   **来源（主机/备机）、原 CSV 行号、主机锚点版本、主机发布版**；备机行标注备机文件号。
   支持 `version=N` 回看历史合并版本，页面下方列出最近合并版本。
4. **原「按日查询」**（`/query`）与 `/api/readings` 完全不受影响，照常只提供主机已校时读数。

### 一致性设计（主机 ↔ 备机）

- **不可变合并快照**：每次合并写入 `merged_results` + `merged_readings`，绑定
  **一个主机已发布校时版本**（`master_calc_version`）和**一个备机文件版本**
  （`backup_file_id`）。主机行与备机行各自记录所属版本，查询按合并版本整体读取，
  绝不混用不同版本的行。
- **提交即在锁内复核**：主机发布新版（`commit_calc`）和备机整批替换都在同一事务内
  递增 `merge_pending_rev`；合并线程按一致快照计算，提交事务内复核合并代次、
  主机发布版与备机 active 文件，任一不符即整次丢弃重算。
- **旧结果只可回看**：主机有上传/锚点变更尚未重算、主机已发布更新的校时版本、
  备机文件已更换、合并待重算或请求历史版本时，`deliverable=false` 并给出原因；
  页面标记「不可交付 / 仅供回看」。旧快照数据完整，但绝不会被当成可交付数据。
- **重启恢复**：合并代次持久化；重启后自动补齐滞后的合并结果。

## 一致性设计

- **原子换版**：每次重算结果在单个事务内整体替换。读数跨日时，
  「旧日移除 + 新日加入」同事务生效；计算或提交失败时旧版本原样保留，
  **绝不提供半版**。
- **迟到计算不回退**：上传/锚点变更递增 `state_generation`；重算按一致快照
  计算，提交前复核代次，已过期则丢弃重算。校时版本号单调递增。
- **重算期间可写可读**：重算在后台线程进行，期间可继续上传新点，
  查询始终看到完整的旧版本；新点在随后的换版中生效。
- **重启恢复**：代次持久化于 SQLite，服务重启后自动比对并补算——
  所有已接纳且处于锚点范围内的点最终都会进入当前版。

## JSON API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/uploads` | 上传 CSV（multipart `file`），返回 `{batch_id, accepted}` |
| POST | `/api/anchors` | 录入/更正锚点 `{segment, local1, utc1, local2, utc2, version?}` |
| GET | `/api/readings?date=YYYY-MM-DD` | 按 UTC 日查询已校时读数 |
| GET | `/api/pending` | 待校时读数及原因 |
| GET | `/api/status` | 点数、重算状态、代次、锚点、批次 |
| POST | `/api/recalc` | 手动触发重算 |
| POST | `/api/backup` | 上传备机 CSV（multipart `file` + 表单 `start`、`end`），整批生效 |
| GET | `/api/merged?date=YYYY-MM-DD[&version=N]` | 按 UTC 日查询合并读数（可回看历史合并版本） |
| GET | `/api/merge/status` | 当前备机文件、合并状态与最近合并版本 |

错误返回 `{detail, code, errors?, current_version?}`；锚点版本冲突为 409，
合并版本不存在为 404，备机 CSV 校验失败为 400（`CSV_INVALID`，附行号）。

## 配置（环境变量）

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `DB_PATH` | `data/app.db`（容器内 `/data/app.db`） | SQLite 路径 |
| `MAX_POINTS` | `2000` | 累计点数上限 |
| `WORKER_ENABLED` | `1` | `0` 时关闭后台线程，变更后同步重算（测试用） |
| `RECALC_DELAY` | `0` | 重算提交前人为延迟秒数（演示/测试并发窗口） |
| `MERGE_DELAY` | `0` | 备机合并提交前人为延迟秒数（演示/测试并发窗口） |

## 已知边界

- 面向单台记录仪、≤2000 点的场景，全量重算代价可忽略，未做增量计算。
- 校时结果毫秒精度；锚点区间与断流区间均按闭区间处理；「超过 5 秒」按毫秒比较。
- 备机文件内的 UTC 冲突会阻断整个断流区间的交付（按需求不做自动取舍），
  需修正文件后重新上传。
- 未实现鉴权与多用户，部署在内网/受信环境。
